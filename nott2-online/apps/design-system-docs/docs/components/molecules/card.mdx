# Card

The surface on which the game's content rests. A diegetic piece of dark wood or aged paper — Card creates depth and separation, grouping related mechanics into a single visual unit. Every variant carries a distinct emotional weight: `instruction` whispers with blood-red authority, `success` glows with survival green, `failure` burns with accentBright, and `ghost` vanishes entirely, leaving only the content.

:::caution
This is a **UI container** component — not a playing card. For the diegetic card face (suit + rank), see [PlayingCard](/components/molecules/playing-card).
:::

<details open>
<summary>Code example</summary>

```tsx
import { Card } from '@nott2/design-system';

<Card variant="instruction" title="Scene Setup">
  <Text>Draw a card from the Threat Deck to determine the encounter.</Text>
</Card>
```
</details>

## Why to Use

Card replaces raw `<div>` grouping with a semantically meaningful surface that carries consistent padding, border radius, border color, background, and interactive states — all from design tokens. Without it, developers inevitably reach for one-off `div` wrappers with hardcoded `padding`, `border`, and `background-color` values, which break visual consistency and resist theming (playsets).

The variant system encodes **emotional meaning**: a `success` card tells the player something went right before they even read the text, because the green border triggers the same "survival" register as Toggle's active state and Badge's success variant. A `failure` card radiates danger before the words land. The colors are a shared vocabulary across the entire system.

## When to Use

In practice, Card serves two distinct roles:

**1. Operational step** — The most common pattern in the game. A Card acts as a discrete workflow unit within a phase screen: a titled prompt, explanatory text, and one or more action controls (buttons, selectors, toggles). Examples: "Award Genre Point?", "Assign 2 Strikes", "Escalation — Something Not Right".

**2. Passive container** — Grouping related display-only content: a scene prompt, a results summary, configuration panels in forms.

> **Do**
> - Use Card as an operational step when the player needs to make a decision — the Card boundary tells them "this is one self-contained thing to resolve".
> - Use `instruction` for GM-directed game mechanics that tell the player what to do (scene prompts, rule explanations).
> - Use `success` and `failure` for outcome-specific steps where the variant reinforces the result before the player reads the text.
> - Use `highlighted` for the currently-selected or active item in a choice list.
> - Use `muted` for de-emphasized, secondary information.
> - Use `ghost` as a layout-only grouping when you need Card's padding structure but no visual surface.
> - Use `interactive` when the entire card surface is clickable (e.g., selecting from a list of options).

> **Don't**
> - Don't use Card for single-line system messages — use [StatusCallout](/components/atoms/status-callout) instead. Cards are for *grouped content sections*; StatusCallout is for *individual announcements*.
> - Don't use `highlighted` for "danger" — use `failure`. The red border on `highlighted` means *active/selected*, not *bad*.
> - Don't nest Cards within Cards — it creates visual clutter. If you need sub-grouping inside a Card, use [Separator](/components/atoms/separator) or layout atoms.
> - Don't use `interactive` without an `onClick` handler — a glowing hover with no response feels broken.

## Content Guidelines

> **Do**
> - Use the `title` prop for Card headers — it renders a consistent `h3` with the display font. Don't render your own `<Text variant="h3">` inside a Card when `title` would suffice.
> - **Operational steps**: Titles are often questions or directives — "Award Genre Point?", "Define the Sacrifice", "Spend Genre Point?". This is correct; the title frames the decision.
> - **Passive containers**: Titles are noun phrases — "Deck Changes", "Weaknesses Found", "Character Names".
> - Follow the title with a brief `caption`-variant explanation, then the controls. This pattern (title → context → action) is used consistently across phase screens.

> **Don't**
> - Don't put long prose directly into a Card without breaking it up with Text variants or Separator.
> - Don't use full sentences as titles — "Here is what you need to do" → "Instructions" or "What do you do?".
> - Don't use Card for purely decorative grouping with no conceptual boundary. If items are related and need spacing, a [Stack](/components/atoms/stack) with a [Separator](/components/atoms/separator) is lighter.

## Anatomy

```
 ┌─ border (variant-colored) ─────────────────────┐
 │                                                 │
 │  [Title]  ← optional h3 via title prop          │
 │                                                 │
 │  ┌─ children ────────────────────────────────┐  │
 │  │  Any React nodes: Text, Stack, Row, etc.  │  │
 │  └───────────────────────────────────────────┘  │
 │                                                 │
 └──── padding: vars.space.lg (24px) ─────────────┘
```

1. **Border** — 1px solid, color determined by `variant`. The border is the primary emotional signal.
2. **Title** — Optional `<h3>` rendered via the `title` prop. Uses `vars.font.display` and `vars.fontSize.h3`.
3. **Children** — Arbitrary React content. The Card imposes no layout on children — use [Stack](/components/atoms/stack) or [Row](/components/atoms/row) inside.
4. **Padding** — `vars.space.lg` on all sides. Removed when `noPadding` is `true`.

## Key Props

Use these props to configure the Card component.

### `variant`
The emotional register of the card surface. Each variant has a distinct background color, border color, and semantic purpose.

| Value | Border | Background | Purpose |
|---|---|---|---|
| `default` | `vars.color.border` | `vars.color.surface` | General content grouping |
| `muted` | `vars.color.border` | `vars.color.background` (70%) | De-emphasized, secondary |
| `highlighted` | `vars.color.borderActive` (red) | `vars.color.surfaceElevated` | Selected / active item |
| `success` | `vars.color.success` (green) | `vars.color.surface` | Positive outcome |
| `failure` | `vars.color.accentBright` (red) | `vars.color.surface` | Negative outcome |
| `instruction` | `vars.color.accent` | Red-tinted transparent | Game directions from the GM |
| `ghost` | Transparent | Transparent | Layout-only, invisible |

### `complete`
Marks the card as a resolved operational step. The border transitions to `success` green, and the title gains a `check_circle` icon. Children remain visible — the information is still relevant after completion.

| Type | Default | Description |
|---|---|---|
| `boolean` | `false` | Green border + checkmark icon on the title. |

Optional text shown below the title when `complete` is true. Provides a brief summary of what was resolved.

|---|---|---|

### `collapsible` & `collapsed`
Controls whether the card's children can be collapsed (hidden) and their current visibility. These are **independent from `complete`** — you can collapse a card that isn't complete, and a complete card can remain expanded.

| Prop | Type | Default | Description |
|---|---|---|---|
| `collapsible` | `boolean` | `false` | Shows a toggle button at the bottom of the card. |
| `collapsed` | `boolean` | `false` | Whether the children are currently hidden. |
| `onToggleCollapse` | `() => void` | `undefined` | Callback fired when the user clicks the toggle. |

  </Card>
</ComponentPreview>

<Card
  title="Rules Modules"

## Behavior

- All variants transition smoothly via `transition: all vars.transition.normal` — border color, background, and box-shadow changes animate on state change.
- `interactive` adds `cursor: pointer` and a hover state that lifts the card by 1px with a blood-red glow. This transition is also smooth.
- `instruction` variant applies `font-style: italic` to the card container, which cascades into all child text. This is an intentional design choice — GM instructions have a distinct voice.
- The `title` prop renders a raw `<h3>` (not a `<Text>` atom). This is a known deviation; it uses the same font tokens directly via `cardTitle` style.
- **Complete**: When `complete={true}`, the border color overrides to `vars.color.success` regardless of the original variant, and a `check_circle` icon appears next to the title (which also turns green). Children remain fully visible — the content is still relevant after completion.
- **Collapsible**: When `collapsible={true}`, a toggle button appears at the bottom of the card. The children area uses a `max-height` + `opacity` transition for smooth expand/collapse animation. `collapsible` and `collapsed` are independent from `complete` — all combinations are valid.

## Accessibility

- Card is a generic `<div>` container with no implicit ARIA role. The content inside determines semantics.
- When `interactive` is true, you should add an `onClick` handler and consider adding `role="button"` and `tabIndex={0}` to ensure keyboard accessibility.
- The `title` prop renders an `<h3>` — be aware of heading hierarchy in the surrounding context.
- The collapse toggle button sets `aria-expanded` to reflect the current state, and has an `aria-label` of "Expand card content" or "Collapse card content".
